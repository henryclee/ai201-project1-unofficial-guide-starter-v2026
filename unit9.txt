Show What You Know: The Capstone
You've built four systems. Every one of them you tested against a standard you wrote before you had any results.

This unit you do it once more, and nothing is handed to you. No brief telling you what the system does. No criteria written for you. No reference set, no attack set, nobody else's answers. Just one of your own systems, a decision about what to do to it, and your own judgment about what would count as that working.

Both halves are due this unit. The build and the test land together. That's different from every other project in this course and it's deliberate — you're extending something that already exists, so the build half is genuinely lighter than starting from scratch.

You're choosing a shape, not inventing one. Three are offered below. Each is bounded to work you've already done.


🎯 Goals
By the end of this unit you'll be able to:

Scope a bounded extension to a system you already built, and finish it in a unit
Put a system somewhere it runs and can be observed — hosted, or locally with a record
Instrument a running system so its behavior is visible after the fact
Say what your system costs to run, from a measurement rather than a guess
Write acceptance criteria with no template, no examples, and nobody handing you two of the five
Run the whole build–test–diagnose–fix cycle unaided

📖 Words you'll need
Term	What it means
Deploy	Putting your system somewhere it runs that isn't your editor. A host, a container, or a documented local run — see the two paths below.
Instrumentation	Code that records what your system did, so you can find out later.
Observability	Being able to answer a question about a running system without adding new code first.
Structured log	A log written as records with named fields, not as sentences.
Latency	How long one request takes end to end.
Cost per run	What one pass through your system costs — in API spend, in tokens, or in seconds of compute.
Scope	What you've decided is in this unit's work, and what you've decided isn't.

🔀 Pick a shape
Pick one. All three extend a system you already built. None of them is easier than the others, and the rubric doesn't care which you pick.

A — Deploy and instrument. Take a system that only ever ran on your laptop and put it somewhere it runs on its own, with logging and measurement around it. The extension is the operational layer: the run path, the instrumentation, and the numbers that come out of it.

B — Harden against failure. Take a system that works when everything goes right and make it survive when things don't. Timeouts, retries, missing input, an API that returns nothing, a rate limit you hit. The extension is the failure handling, and your criteria are about what happens on the bad path.

C — Extend one capability. Add ONE real capability to a system that already works — a second retrieval strategy, a fourth tool, a new label, an endpoint. The extension is the capability plus the evidence that it does what you claim.

Whichever you pick, all three still deploy and instrument — shape A just makes that the whole job, while B and C carry it alongside. The run path and the log are required in every case.

⚠️ The one rule about scope. You are extending a system that exists. You are not starting one. If your plan involves the words "rewrite," "from scratch," or "a new project," it's the wrong plan — and the reason isn't the schedule, it's that a system you've already built is the only kind you know well enough to have real opinions about.

🚀 Two ways to run it — pick one, they're worth the same
Putting a system online usually means signing up with a host, and most free plans ask for a credit card. That's a real barrier and it isn't part of what this course teaches. So there are two paths, and the rubric treats them identically.

Path A — hosted. Your system runs somewhere with a URL. You include the URL, the platform, and the command or config that gets it there, plus everything Path B asks for below.

Path B — local with logs. Your system runs on your machine, started by a single documented command, with a committed record of it actually running. You include:

The exact command that starts it, in RUNNING.md, tested from a clean checkout
A committed run record — your structured log from a real session, pasted as text
What the environment needs: Python version, the pinned dependencies, any model files and their size
Neither path is a downgrade, and Path B is the one most of you will take. That isn't a hedge — it's arithmetic. The free hosting tier this course uses gives you 512 MB of memory, which is fine for a system that just calls an API and nowhere near enough for one that loads a model locally. If your system carries a local model, Path B is the right answer and you can stop reading this section.

Path B asks you to make the run reproducible for someone who isn't you, which is most of what deployment actually is. What both paths must prove is the same thing: this ran somewhere, more than once, and there's a record of it.

If you're on Path A, the platform and its setup are on the environment setup page. If a signup asks for a card and you'd rather not, take Path B. You don't need to ask anyone, and it doesn't cost you a point.

Two things to know if you're on Path A.

Your log doesn't survive. Free instances get wiped when they go to sleep, which happens after about fifteen minutes of nobody using them. So copy your log entries into your README and commit them the same session you produce them. The version in your repo is the one that counts, and on a free host it's the only one that lasts.

Your first request after a quiet period is slow. The service sleeps and takes about a minute to wake up. If you're writing a criterion about response time, decide now whether you mean a warm request or any request — and say which in the criterion. Finding out in Milestone 5 that your target measured something you didn't intend is a real result, but it's a better unit if you thought about it first.


📦 What proves you did the work
Six things — three for the build half, three for the test half. Everything lands this unit, in the same repository as the system you're extending.

Build half

criteria.md — five numbered acceptance criteria, all yours, written before you have results.
README.md — the build sections listed at the bottom of this page, including which shape you picked and what's out of scope.
RUNNING.md — the run path. A URL and how it got there, or the single command and the environment it needs.
Test half

A run log — your five criteria, three trials each, before your fix and after it.
A verdict and a diagnosis — met or missed per criterion, and what caused every miss.
A cost measurement — what one run costs, and how you worked that out.

✅ What's required

One system, extended. One of your four. Say which, and say what's new.


One shape, declared. A, B, or C, named in your README, with a sentence on what you decided is out of scope.


A run path that isn't your editor. Path A or Path B. RUNNING.md holds it.


Structured logging. Every run writes a record with named fields — at minimum a timestamp, what came in, what came out, and how long it took. Pasted extract in the README, at least ten entries.


A cost number. What one run costs you: API spend, tokens, or seconds of compute. Measured, not estimated from the docs. Say how you got it.


Five acceptance criteria, written by you before you run anything. No template. At least three of the five must be about the extension, not about the system as it already worked.


Three trials per criterion. One run is not a test. Anything touching a model can come out differently twice.


A verdict and a diagnosis for each criterion. Met or missed against your own target, and for every miss, which part of the system and how.


One improvement, made and measured. One change, re-run, both result sets side by side.


A written call on what's left. What you'd do, and why you stopped.

Stretch
Optional, extra credit. Say what you're adding in your README before you start.

A second measured improvement, run and logged the way the first one was.
A latency breakdown — where the time actually goes across the stages of one run, measured.
A load observation — run the system at ten times your normal rate and report what changed.
Both run paths — deployed and documented locally, with a note on what differed between them.

🛠️ Setup
Nothing new to install for the extension itself. Your system's existing setup is what it was.

Use the same repository as the system you're extending. Not a copy, not a fresh repo — the one you already submitted. Two reasons. Your extension is only legible as an extension next to what came before it. And because both halves land in the same unit, your commit history is what shows your criteria existed before your results did, so commit criteria.md before you run anything, give that commit and your first results commit messages that name them, and don't rewrite history afterwards.

If your chosen system doesn't currently run, talk to your TF early in the unit.. There's a way to get you a working version, and the unit is too tight to lose two days to it.



Milestone 1: Pick the system, pick the shape, cut the scope
⏰ ~35 min · start in your breakout

The failure mode of this unit isn't difficulty. It's scope.

So decide before you build, and write the decision down where it can be checked.


Pick the system — the one you understand best. You'll be writing criteria about its failure modes from memory, and that's much easier on a system whose weak points you already know.


Pick the shape: A, B, or C. Write one paragraph in your README under The Shape saying what you're adding.


Write what's out of scope. Two or three things you thought about doing and decided not to. This is the part people skip and it's the part that saves the unit. "I'm not adding a second retriever, I'm not touching the chunking, and I'm not rebuilding the interface" is a real answer.


Sanity-check the size. If your extension needs more than about ninety minutes of building, it's too big — the rest of the unit is the run path, the criteria, the testing, and the write-up. Cut it now, not on Thursday.

💬 Talk this through

In your breakout: this unit's opener is a standup on scope. Say which system you're extending and what you'll claim it does when you're finished — one or two sentences, no more.

Then let people push. The question worth being asked is "is that one thing or three?"

Working on your own? Paste your plan into Claude and ask:

"Here is a one-unit extension I'm planning to an existing system. Break it into the separate pieces of work it actually contains, and tell me how many of them there are. Don't tell me whether it's achievable and don't suggest a smaller version."

Count the pieces. If there's more than one, cut until there's one.

📍 Before you move on

Your README names the system, the shape, and what's out of scope. Commit.



Milestone 2: Build the extension
⏰ ~90 min

Build the thing you scoped in Milestone 1. Nothing more.

This is the only milestone this unit where you're writing feature code, and it's deliberately the shortest build block in the course. Everything you learned about the build units applies — get one path working end to end before you make it good.


Build it. One capability, one hardening layer, or the operational scaffolding — whatever your shape named.


Confirm the original system still works. An extension that breaks what it extends is a regression, and you'll find it faster now than in Milestone 5.


Commit as you go. At least three commits in this milestone alone.

🛑 If you're stuck

Extension not working after an hour? Cut it down, don't push through. A smaller extension that runs, is instrumented, and is tested honestly scores higher than an ambitious one that doesn't run — the points this unit are in the criteria, the testing, and the diagnosis, and none of those need your extension to be impressive.

Write down what you cut and why. That sentence belongs in What's Still Broken and it earns credit there.

📍 Before you move on

The extension does something you can demonstrate, and the original system still works. Commit.



Milestone 3: Get it running, and make it observable
⏰ ~75 min

You built this alongside the instructor in the first half of class. Now do it to your own system.

Two things happen here, in this order: it runs somewhere that isn't your editor, and it records what it did. The second one is what makes Milestone 5 possible — you cannot diagnose what you didn't record.


Pick your path — hosted or local-with-logs — and write RUNNING.md. A URL and how it got there, or the exact start command and what the environment needs.


Test the instructions on yourself. Clone your own repo into a new folder and follow your own RUNNING.md. It will fail the first time. Whatever was missing is the thing a reader would have hit.


Add structured logging. Every run writes a record with named fields — timestamp, input, output, duration, and anything specific to your system worth knowing later. A file you can read back, not print().


Log the failures too. A run that errored should leave a record. A failure that shows up only as an absence is one you'll never find.


Measure the cost of one run. API spend, tokens consumed, or seconds of compute — whichever is the real cost for your system. Run it ten times, take the average, and write down how you measured it. A number from the pricing page isn't a measurement.


Paste at least ten log entries into your README under Instrumentation, and the cost number with its method under What It Costs.

🛑 If you're stuck

Deployment fighting you after forty-five minutes? Switch to Path B. It's worth the same, it costs you nothing, and the time is better spent on the testing half. Note the switch in your README — "I tried to host this and hit X, so it runs locally" is a perfectly good sentence and it's honest engineering.

Can't get a cost number? Time the run instead and say that's what you measured. Seconds of compute is a real cost. Reporting the wrong-but-measured thing beats reporting nothing.

📍 Before you move on

Your system starts from RUNNING.md alone. Ten log entries and a measured cost number are in your README. Commit.



Milestone 4: Write your criteria, unaided
⏰ ~45 min

This is the milestone the whole course has been building toward.

No template. No worked examples. Nobody has written two of them for you. There is a self-check and there are four projects' worth of practice, and that's what you have.

Write these before you run anything. Commit them before you commit any results — your commit history is what shows that order, and this is the one unit where both halves land close enough together that it matters.


Write five numbered criteria in criteria.md. At least three must be about the extension — the thing that's new. Criteria about the parts that already worked are the safe ones, and five safe criteria make for a unit with nothing to learn.


Give each one a target: a number, a rate, or something a person could plainly see. If the sentence turns on works, reliable, good, or fast, it isn't a criterion yet.


Under each, say why that target and not a stricter or looser one. The reason should reference something about your system or what being wrong would cost.


Make sure at least one of them is about what happens when things go wrong — an error, a timeout, an empty result, a bad input. Every one of your four systems has a bad path, and it's where the interesting failures live.


Run your five through the criteria self-check before you commit them. Two minutes now saves a day of testing something you can't measure.

⚠️ On AI tools: don't ask a model to write these. Ask it whether each one could be checked by a person who couldn't ask you what you meant. A criterion you didn't write is one you can't defend, and the whole point of this unit is that you wrote them.
💬 Talk this through

In your breakout — this is the unit 9 checkpoint. Once your criteria are drafted, pair up and review each other's against the self-check. Ask the three questions on that page, in order, and give it a real five minutes each way.

The third question — what would have to happen for this to fail? — finds more problems than the other two combined. If your partner can't picture yours failing, your target is too low.

Working on your own? Paste your five into Claude and ask:

"Here are five acceptance criteria for a system I extended. For each one: how exactly would you test it using only the sentence itself, would two people score it the same way, and what would have to happen for it to fail? Don't rewrite them."

📍 Before you move on

criteria.md has five numbered criteria with targets and reasons, at least three about the extension. Committed, before any results exist. Commit now — the order is the point. Give that commit a message that names it, like add capstone criteria, and do the same when you commit your first results. The order only reads if the messages say which is which.



Milestone 5: Run the test
⏰ ~50 min

Three trials each, changing nothing in between.

Nobody wrote a test set for you this unit. Work out what each criterion actually needs run against it, then run it.


For each criterion, decide what has to be run to produce its number. A criterion about failure handling needs failures — trigger them deliberately. A criterion about latency needs enough runs to have a distribution rather than one number.


Run everything three separate times and save the real output. Then fill in the run log. Every test unit in this course uses the same format — one row for each of your five criteria, a column per run, and a verdict. A table with fewer than five rows isn't a complete run log:

| Criterion | Target | Run 1 | Run 2 | Run 3 | Verdict |
|---|---|---|---|---|---|
| 1. Deployed endpoint answers under 5s | 9 of 10 | 8/10 | 9/10 | 7/10 | MISSED |
| 2. Timeout returns a message, not a crash | 5 of 5 | 5/5 | 5/5 | 5/5 | MET |
| 3. Every run appears in the log | 10 of 10 | 10/10 | 10/10 | 9/10 | MISSED |
| 4. Cost per run stays under $0.01 | 10 of 10 | 10/10 | 10/10 | 10/10 | MET |
| 5. Malformed input gets a 400, not a 500 | 5 of 5 | 5/5 | 4/5 | 5/5 | MISSED |

Underneath the table, paste real output for each criterion from one of the runs — the actual log lines or responses, not a description of them. Name the file and function that produced it.

📍 Before you move on

Five criteria, three trials each, with pasted output underneath. Commit.

If a criterion involving a model came out identical three times, check you're really re-running.



Milestone 6: Call every criterion, diagnose every miss, fix one
⏰ ~1 hr 10 min

The verdict, the diagnosis, and the one improvement — the part of every test unit that carries the points, done here without a brief telling you which stages to look at.


Write MET or MISSED next to each criterion, against the target you set in Milestone 4. If your target said 9 of 10 and your trials came out 8, 9, 7 — that's a miss. The target has to hold, not turn up sometimes.


For each miss, name where and how. You know your system's stages better than any brief could tell you — name the one that produced the failure and the mechanism that made it.

Not a diagnosis:

"It was slower than I expected."

A diagnosis:

"Three of ten runs came back over 5 seconds. All three had queries that matched more than twelve chunks, and my reranker scores every match serially before it truncates. The stage is the reranker; the mechanism is that its cost scales with match count, and my criterion assumed it scaled with result count."


Look for a pattern. If three misses all trace to the same stage, that's one problem with three symptoms, and saying so is worth more than three separate explanations.


Pick one improvement, make it, and re-run. One. Follow the diagnosis — the fix should be aimed at something you just explained. Then run the full set again, three trials each, in the same format.


Put both result sets in the README, before and after, so the difference is visible side by side. Then say whether it helped. If it didn't, say that. A change that made one thing better and another worse, honestly reported with the trade named, earns full credit.

A note on changing a criterion

Sometimes a criterion turns out to be broken rather than unmet. That earns credit — but only one kind of change counts.

✅ This earns points. The criterion couldn't be measured:

Original: "The deployed system is reliable under load." Revised: "At 10 requests per minute, at least 9 of 10 return a response rather than an error." Why: "reliable" gave me nothing to check. I couldn't reach a verdict from it.

❌ This does not. The criterion was fine; you missed it:

Original: "9 of 10 responses come back under 5 seconds." Revised: "7 of 10 responses come back under 5 seconds." Why: 9 turned out to be hard.

If you revise, leave the original line and put the new one underneath with your reason. Never delete the original.
🛑 If you're stuck

Improvement not working after forty minutes? Keep what you have, put both result sets in anyway, and write down what you tried and where it broke. A failed improvement you can explain is a complete submission.

📍 Before you move on

Every criterion has a verdict. Every miss names a stage and a mechanism. Both result sets are in the README. Commit.



Milestone 7: Cost, what's left, and submit
⏰ ~30 min

The last write-up in the course.


Finish What It Costs. Your measured per-run number, how you measured it, and one sentence on what it would cost to run this for a hundred people a day. Show the arithmetic — it's multiplication, and the point is that you can produce the number rather than wave at it.


Write What's Still Broken. For each criterion still missed: what you'd do, and why you stopped. "I ran out of time" is fine if it's true.


Add two sentences on what you'd do next if this were real and you had another unit. Not a wish list — the one thing you'd do first, and why that one.


Update How I Used AI, check the repo against the submission list below, and submit the URL.

📍 Before you move on

Both result sets, verdicts, diagnoses, the cost number, and your call on what's left. Same repository as the system you extended. Commit.

🗺️ How it's graded
The full breakdown of graded features and points is on the course grading page.

60 points — 30 for the build half, 30 for the test half. Both are submitted this unit.

The build half asks three questions:

Did you extend a system you built, and can a reader see what's new and what's out of scope?
Does it run somewhere that isn't your editor, with a record of it running?
Are your criteria real criteria — specific, testable, carrying targets, and mostly about the extension?
The test half asks three more:

Did the runs actually happen, enough times to produce the measures your criteria named?
Are the verdicts right, given what your own runs produced?
Does the diagnosis name a mechanism, and does the improvement follow from it?
Missing your own criteria does not cost you points. A capstone that missed all five, diagnosed each one clearly, and reported an improvement that didn't help earns full marks. Which shape you picked doesn't affect your score, and neither does which run path. What's graded is whether you set an honest standard on a system nobody scoped for you, and tested against it.
